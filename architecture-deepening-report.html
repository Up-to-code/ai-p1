1. Shallow Pipeline Factory

High

Files Involved

  • convex/pipeline_core.ts (214 lines)
  • convex/deals/read.ts (111 lines)
  • convex/deals/write.ts (97 lines)
  • convex/opportunities/read.ts, write.ts
  • convex/clients/read.ts, write.ts
  • convex/projects/read.ts, write.ts

Problem

The pipeline_core.ts module exports factory functions (createPipelineList, createPipelineCreate, etc.) that generate Convex query/mutation handlers from a PipelineConfig object. However, no one is using these factories — the deals/ module has completely duplicated the same logic inline.

This is a classic shallow module: the factory's interface (PipelineConfig with 7 fields) is nearly as complex as understanding the generated code itself. The factories were meant to provide leverage (one implementation, many callers), but since they're unused, they're providing zero locality — bugs in deals/read.ts won't be fixed in the factory, and vice versa.

Evidence

grep -r "createPipeline" finds only the factory definitions, no callers
deals/read.ts:list (lines 28-52) is a 95% copy of createPipelineList's handler
deals/write.ts:createFromHono (lines 11-42) duplicates createPipelineCreate

Deletion Test

If you delete pipeline_core.ts, nothing breaks — no callers exist. The domain-specific code in deals/ is actually clearer because it uses concrete types, not any casts.

Solution Options

Option A (Delete the factory): Remove pipeline_core.ts entirely. The duplicated code in each domain module is more maintainable because it uses proper types and is easier to understand.
Option B (Make it earn its keep): Migrate all pipeline entities (deals, opportunities, etc.) to use the factory, but deepen it by extracting the shared CRUD+audit pattern into a proper workspace entity lifecycle module that handles auth, validation, persistence, and audit in one place with a small, stable interface.

Benefits of Deepening

  • Testability: Currently untestable because the factories return Convex handler objects. A deepened module would expose pure lifecycle functions (e.g., createEntity, updateEntity) that can be unit-tested without Convex runtime
  • Locality: Bug fixes in CRUD logic apply to all entities, not just one
  • Leverage: One well-tested implementation serves all pipeline domains

2. Scattered Presentation Logic

Medium

Files Involved (25+ duplicate present functions)

  • convex/shared/present.ts (generic presentWorkspaceRecord)
  • convex/deals/read.ts:9-11 (presentDeal)
  • convex/deals/write.ts:7-9 (presentDeal — identical!)
  • convex/clients/read.ts:31 (presentClient — async)
  • convex/clients/write.ts:22 (presentClient — different!)
  • convex/admin/domainAdapters.ts:116-265 (10+ summary functions)
  • convex/opportunities/read.ts, write.ts (presentOpportunity)
  • convex/projects/read.ts, write.ts (presentProject)
  • convex/clientTasks/read.ts, write.ts (presentTask)
  • convex/clientFollowUps/read.ts, write.ts (presentFollowUp)
  • convex/clientDocs/read.ts, write.ts (presentDoc)
  • convex/projectSpaces/write.ts (presentSpace)
  • convex/organizationApiKeyLifecycle.ts:27 (presentOrganizationApiKey)
  • convex/mcp/connectionLifecycle.ts:30 (presentMcpConnection)
  • convex/billing/data.ts:84,105 (presentPayment, presentSubscription)

Problem

Nearly every module defines its own present* function that does { ...doc, id: doc._id }. This is duplicated pass-through logic with slight variations. The interface for presentation is inconsistent:

  • Some add id, some don't
  • Some handle visibility defaults
  • Some strip deletedAt/isDeleted fields
  • Some do async operations (e.g., presentClient in clients/read.ts is async)

The shared/present.ts module tries to be the seam, but callers ignore it and define their own. This suggests the shared interface doesn't match caller needs.

Evidence

// In shared/present.ts (generic)
export function presentWorkspaceRecord<T extends { _id: string }>(doc: T) {
  return { ...doc, id: doc._id };
}

// In deals/read.ts (duplicate)
function presentDeal<TDeal extends { _id: string }>(deal: TDeal) {
  return { ...deal, id: deal._id };
}

// In organizationApiKeyLifecycle.ts (complex, earns its keep)
export function presentOrganizationApiKey(key, now = Date.now()) {
  return {
    status: organizationApiKeyStatus(key, now),
    quotaLimit: ORGANIZATION_API_KEY_QUOTA_LIMIT,
    quotaUsed: key.quotaUsed ?? 0,
    // ... 15 more computed fields
  };
}

Deletion Test

If you delete shared/present.ts, nothing breaks — callers already have their own copies. But if you try to consolidate them, you'll discover the real complexity: presentation is coupled to domain semantics (e.g., presentOrganizationApiKey computes status, quota, TTL).

Solution

Create deepened presentation modules per domain entity: Instead of a generic shared/present.ts, create domain-specific presentation modules that encapsulate all presentation rules: ID projection, status computation, field redaction, visibility defaults.

Benefits

  • Locality: Changing how deals are presented only requires editing one place, not synchronizing deals/read.ts and deals/write.ts
  • Testability: Tests verify presentation invariants (e.g., "revoked keys show correct status", "client PII is protected in list views") at the seam
  • Consistency: All callers get the same presentation logic, no drift

3. Admin Domain Adapter — Massive Conditional Dispatch

High

Files Involved

  • convex/admin/domainAdapters.ts (621 lines)
  • convex/admin/listSurface.ts (43 lines)
  • convex/admin/organizationDashboard.ts (92 lines)

Problem

The domainAdapters.ts file implements a DomainAdapter interface with list, find, summarize, detailRaw, and runAction methods. But the implementation is a 600-line switch statement that handles 11 different admin domains:

  • organizations
  • users
  • apps
  • oauth-clients
  • partner-connections
  • api-keys
  • mcp-connections
  • webhooks
  • ai-activity
  • audit-logs
  • workspace-data

Each domain has custom list query logic, custom summary formatter, custom action handlers (approve, reject, suspend, revoke, etc.), and custom detail enrichment.

This is a shallow adapter: the interface promises polymorphism, but the implementation is a massive conditional that knows about every domain. Adding a 12th domain requires editing this file in 5+ places.

Evidence

// Lines 300-500: giant conditional chains
if (domain === "organizations") { /* 80 lines */ }
else if (domain === "users") { /* 40 lines */ }
else if (domain === "api-keys") { /* 50 lines */ }
else if (domain === "mcp-connections") { /* 45 lines */ }
else if (domain === "webhooks") { /* 60 lines */ }
// ... 6 more domains

// No test file for domainAdapters.ts (too hard to test through this interface)

Deletion Test

If you delete domainAdapters.ts, the admin UI breaks completely — this module is earning its keep. But the current architecture makes it a bottleneck for adding new domains.

Solution

Extract per-domain adapters: Move each domain's adapter logic into its own file (e.g., admin/organizationsAdapter.ts, admin/usersAdapter.ts). The domainAdapters.ts file becomes a thin registry that imports and exports adapters.

Benefits

  • Locality: Understanding how admin actions work for API keys only requires reading one file, not finding the right else if branch in a 600-line file
  • Testability: Each adapter can be tested independently with focused test cases
  • Leverage: The DomainAdapter interface becomes real — new domains implement it without modifying existing code
  • Open-Closed Principle: Open for extension (new adapters), closed for modification (existing adapters unchanged)

4. Partner Resource Gateway — God Function for CRUD

Medium

Files Involved

  • convex/partnerResourceGateway.ts (345 lines)
  • convex/organizationApiKeys.ts:140-183 (calls the gateway)
  • convex/partnerResourceGateway.test.ts (264 lines)

Problem

readPartnerResourceThroughGateway and writePartnerResourceThroughGateway are god functions that handle CRUD for 7 different resource types through conditional dispatch:

  • organization
  • client
  • project
  • task
  • calendar
  • media
  • asset

The read function (lines 201-270) has 7 if (args.resource === ...) branches, each implementing different query logic:

  • Organization: single record lookup
  • Client/Project/Task/Calendar: list or single by ID
  • Media: filtered by resourceType + resourceId

The write function (lines 272-344) only supports client, but throws for all other resources. This is misleading — the interface promises polymorphism but the implementation rejects 6/7 resources.

Coupling Issues

  • Client PII protection logic is inline (lines 280-302)
  • Audit event creation is duplicated for partner apps vs API keys
  • Webhook enqueueing is mixed in (line 198)

Evidence

// readPartnerResourceThroughGateway (270 lines)
if (args.resource === "organization") { /* 10 lines */ }
if (args.resource === "client") { /* 20 lines */ }
if (args.resource === "project") { /* 15 lines */ }
if (args.resource === "task") { /* 15 lines */ }
if (args.resource === "calendar") { /* 15 lines */ }
if (args.resource === "media") { /* 20 lines */ }

// writePartnerResourceThroughGateway (344 lines)
if (args.resource !== "client") throw new Error(...);
// Only client is supported! 6/7 resources throw

Deletion Test

If you delete partnerResourceGateway.ts, partner API integration breaks completely — this module is earning its keep. But the god function pattern makes it hard to understand and test individual resource handlers.

Solution

Extract per-resource handlers: Create separate modules for each resource (e.g., partnerGateway/clientHandler.ts, partnerGateway/projectHandler.ts). The gateway becomes a thin router that delegates to handlers.

Benefits

  • Locality: Client PII protection changes only require editing one handler, not understanding the whole gateway
  • Testability: Each handler can be tested with focused inputs/outputs
  • Honest interface: If write only supports client, the type system should reflect that (not promise 7 resources and throw for 6)
  • Separation of concerns: Webhook logic, PII protection, and audit creation are separated from routing logic

Recommended Next Steps

Prioritize based on impact and effort:

  1. Immediate: Delete pipeline_core.ts (Candidate 1) — it's unused and provides zero value
  2. Short-term: Extract admin domain adapters (Candidate 3) — 600-line file is a maintenance bottleneck
  3. Medium-term: Deepen presentation logic (Candidate 2) — consolidate 25+ duplicates into domain-specific modules
  4. Medium-term: Refactor partner gateway (Candidate 4) — extract per-resource handlers for better testability

Glossary

  • Module: Anything with an interface and an implementation (function, class, package)
  • Interface: Everything a caller must know to use the module: types, invariants, error modes
  • Depth: Leverage at the interface — a lot of behaviour behind a small interface
  • Shallow: Interface nearly as complex as the implementation
  • Seam: Where an interface lives; a place behaviour can be altered without editing in place
  • Locality: Change, bugs, knowledge concentrated in one place
  • Leverage: What callers get from depth
