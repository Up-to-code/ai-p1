01
State Management — 5 Competing Systems CRITICAL
68+ files across 10 domains · clients.store.ts · projects.store.ts · calendar.store.ts · tasks/api/tasks.ts · domains/clients/api/clients.ts
Problem
The codebase uses 5 state management patterns simultaneously: Zustand (dead stores, never sync), TanStack Query (primary CRUD), Convex useQuery (real-time subscriptions), React Context (auth/navigation), and custom hooks with useState. The same data — clients, tasks — flows through 2–3 systems at once with no sync strategy. The deletion test: delete Zustand stores → complexity does not reappear (dead code). Three systems earn their keep but compete.
Solution
Adopt TanStack Query as the single server state layer. Keep Convex only for real-time features (chat, notifications). Delete all Zustand stores (~300 lines). Replace useOptimisticTaskActions (124 lines) with TanStack Query's built-in onMutate/onError. Tasks are the only domain not aligned with this pattern.
Benefits
  • Locality — one mutation/query pattern to learn, one cache invalidation strategy
  • Leverage — delete ~300 lines of dead/store code
  • Tests — mock one query client instead of mocking Convex + TanStack Query + localStorage
02
project-detail-overview.tsx — 1,292-Line Monolith CRITICAL
domains/projects/components/project-detail-overview.tsx
Problem
One file exports 7 view components with 30+ useState calls, 15+ useMemo/useCallback, and static data (STATUS_COLORS, PRIORITY_COLORS, COUNTRY_FLAGS) all inline. The TaskTableView alone is ~560 lines with AG-Grid column definitions, inline cell editors, custom field wiring, filtering, sorting, grouping, and saved views. Impossible to navigate, test, or maintain.
Solution
Split into 7 files under domains/projects/components/views/ — one per view component (table, list, board, calendar, timeline, map) plus a barrel export. Each file owns its static data, state, and rendering.
Benefits
  • Locality — change TaskListView without touching TaskTableView's 560 lines
  • Leverage — 7 focused modules replace 1 incomprehensible one
  • Tests — each view independently testable; no more fixture setup for the entire file
03
Optimistic Update — Two Systems for Tasks HIGH
hooks/use-optimistic-actions.ts · api/task-pipeline-mutations.ts · ws/_pages/board-view.tsx
Problem
Tasks have a custom optimistic action queue (push/reconcile/applyToList — 124 lines) AND a TanStack Query onMutate mutation. Board-view used both simultaneously. The custom system duplicates what TanStack Query provides for free, including cache snapshots, rollback, and invalidation.
Solution
Delete use-optimistic-actions.ts. All task mutations use TanStack Query's built-in optimistic updates. Board-view's pushOptimistic becomes a queryClient.setQueryData call inside the mutation's onMutate.
Benefits
  • Locality — one mutation path for tasks (matches clients/projects/deals)
  • Leverage — delete 124 lines of custom orchestration
  • Tests — test mutations via TanStack Query utilities, not a custom action queue
04
"use client" on 223 Files Including Pure Utilities HIGH
223 "use client" directives in src/domains/ · pipeline-command.ts · tasks.types.ts · task-pipeline-order.ts
Problem
Pure utility files and type definitions are marked "use client", forcing them into the client bundle and preventing server components from importing them. This bloats the initial JS payload for no benefit.
Solution
Remove "use client" from all files with no hooks, event handlers, or browser APIs. Add it only where useState, useEffect, onClick, or localStorage are used.
Benefits
  • Leverage — smaller client bundle, more server-rendered content
  • Locality — the "use client" boundary is explicit and meaningful
05
localStorage — 11 Files, 5 Key Patterns, No Consistency HIGH
11 files across 4 domains · clients-screens.tsx · project-detail-overview.tsx · use-dashboard-persistence.ts · tasks.ts
Problem
No standard for key naming, error handling, SSR guards, or schema migration. Some keys use kebab-case, others use dotted paths, others use template literals with IDs. The "workspace-layout" vs "workspace-widgets" key mismatch was a real data loss bug.
Solution
A single useLocalStorage<T>(key, defaultValue) hook with built-in SSR safety, JSON serialization, and error handling. Key names live in a single storage-keys.ts config.
Benefits
  • Locality — change serialization format in one place
  • Leverage — 11 files stop re-implementing the same boilerplate
  • Tests — test the hook once; mock localStorage in one test helper
06
Barrel Exports — 3 Domains Missing, 9 Using Wildcards MEDIUM
tasks/ · cache/ · media/ · custom-fields/ (no barrel) · clients/ · calendar/ · deals/ (wildcard export *)
Problem
Domains without barrel exports force deep imports like @/domains/tasks/hooks/use-task-mutations. Domains with export * leak internal types (Zustand stores, internal hooks). Both patterns defeat module encapsulation.
Solution
Every domain gets a hand-crafted index.ts with explicit named exports. Only the public API surface is exported. Internal types stay private.
Benefits
  • Leverage — rename a file or restructure a domain without breaking 20 import paths
  • Tests — the barrel is the contract; test against it
07
Auth Context — 83 Importers, 95% Use Only One Export MEDIUM
domains/auth/ (188-line context hook) · 83 importing files
Problem
The auth context is a monolith with 30+ fields in 3 nested objects. All 83 consumers get the entire object identity regardless of which field they need. The workspace.organizationId derivation (status === "ready") is duplicated 52 times across the codebase.
Solution
Add a selector function useOrgId(): string | null that extracts the org ID with a stable reference. Consider splitting into useWorkspaceContext, useUserContext, useOrganizationContext with separate providers.
Benefits
  • Locality — change org ID derivation logic in one function
  • Leverage — 52 call sites stop duplicating the same ternary expression
  • Tests — the selector is the test surface for org ID logic

Glossary

Module — anything with an interface and an implementation. Depth — leverage at the interface: a lot of behaviour behind a small interface. Seam — where an interface lives; a place behaviour can be altered without editing in place. Locality — what maintainers get from depth: change, bugs, knowledge concentrated in one place.
